# 탐색기 Space 미리보기

## 실행과 조작

1. 저장소 루트에서 `dotnet build -m:1`을 실행합니다.
2. `src\MoaView\bin\Debug\net8.0-windows10.0.19041.0\MoaView.exe`를 실행합니다. 현재 개발용 빌드는 .NET 8 Windows Desktop Runtime이 필요합니다.
3. 기본 창의 **설정 → 탐색기 → Space 키로 미리보기**를 확인합니다. 기본 창을 닫아도 트레이에서 계속 실행됩니다.
4. Windows 탐색기의 파일 목록에서 파일 하나를 선택하고 `Space`를 누릅니다.
5. 탐색기에서 방향키나 마우스로 다른 파일을 선택하면 열린 미리보기 내용이 바뀝니다.
6. 탐색기에서 다시 `Space`를 누르면 미리보기가 닫힙니다. 미리보기 창을 직접 클릭해 활성화한 경우에는 `Space`, `Esc`, 창의 닫기 버튼을 사용할 수 있습니다.

별도 미리보기 창에서도 확대·축소·회전·형식 변환을 사용할 수 있습니다. 기본 창의 이미지와 미리보기 창의 이미지는 각각 관리됩니다. 선택 파일이 그대로인 동안에는 탐색기를 반복 조회하더라도 확대·회전 상태를 초기화하지 않습니다.

설정이나 트레이 우클릭 메뉴에서 **Space 키로 미리보기**를 해제하면 Space 연동과 열린 미리보기가 종료됩니다. 기본 창을 닫으면 해당 창의 동영상·문서 자원을 해제하고 트레이만 유지합니다. 트레이 아이콘 더블클릭이나 **MoaView 열기**로 새 기본 창을 열 수 있습니다. 앱을 완전히 종료하려면 트레이 메뉴의 **MoaView 종료**를 선택합니다. 다음 실행에서는 Space 연동이 다시 켜진 상태로 시작합니다.

**설정 → 탐색기 → Windows와 함께 시작**을 켜면 다음 로그인부터 `MoaView.exe --background`로 실행되어 창을 띄우지 않고 Space를 기다립니다. 기본은 꺼짐이며 설치 프로그램에서도 선택할 수 있습니다. 등록은 현재 사용자 계정에만 적용되고, 설정을 끄거나 앱을 제거하면 해제됩니다. Windows 작업 관리자의 시작 앱에서 별도로 차단한 경우에는 그곳에서도 사용으로 변경해야 합니다. 개발 빌드·이동식 실행 파일은 등록한 경로를 유지해야 합니다.

설치본에서는 파일 하나를 우클릭한 뒤 **MoaView로 미리보기**로 열 수도 있습니다. Windows 11에서는 **추가 옵션 표시** 안에 있습니다. 이 메뉴는 필요할 때 미리보기 창만 실행하며 Space 또는 Esc로 닫을 수 있습니다. 설치 프로그램이 현재 사용자 메뉴를 등록하고 제거 시 정리합니다.

## 지원 범위와 예외

- Windows 탐색기 파일 목록의 단일 파일 시스템 항목을 대상으로 합니다. 바탕 화면, 파일 열기 대화상자, 다른 파일 관리자, 가상 Shell 항목은 대상이 아닙니다.
- 주소창, 검색창, 파일 이름 변경, 메뉴 사용 중에는 Space의 원래 입력을 유지합니다. `Ctrl`·`Alt`·`Shift`·Windows 키와 함께 누르는 Space도 연동 대상이 아닙니다.
- 선택이 없거나 여러 항목을 선택한 경우 미리보기는 열리지 않습니다. 파일 목록에서는 이 경우에도 Space 입력을 소비합니다. 열린 상태에서 선택을 해제하거나 다중 선택으로 바꾸면 미리보기가 닫힙니다.
- 지원 이미지, 손상 이미지, 미지원 파일, 폴더의 표시는 기존 미리보기 결과를 그대로 사용합니다. 폴더·미지원 파일은 지원하지 않는다는 안내를 표시합니다.
- 같은 탐색기 창의 선택을 약 200ms 간격으로 확인합니다. 다른 탐색기 창의 파일 목록으로 이동하면 기존 미리보기가 닫히며, 그 창에서 Space를 누르면 새로 열립니다. 주기 갱신 전에 다른 창·탭에서 Space를 눌러도 새 선택을 열며, 이전 Shell 조회가 늦게 끝나는 경우 마지막 열기 요청 하나만 유지합니다. 닫기·종료·포커스 변경 뒤에는 대기 중인 요청으로 창을 다시 열지 않습니다. 다른 앱이나 주소창으로 포커스를 옮긴 경우에는 선택 조회를 중지하고 기존 창을 유지합니다.
- 미리보기는 탐색기의 소유 창으로 표시되어 탐색기 위에 놓이며 다른 모든 앱 위에 고정하지 않습니다. 파일 읽기와 이미지 디코딩은 기존 동기 로더를 사용하므로 큰 파일이나 느린 네트워크 경로에서는 표시가 지연될 수 있습니다.
- 일반 실행은 사용자·세션당 하나의 상주 프로세스를 사용합니다. 다시 실행하면 기존 창을 열고, 파일 인수도 그 창에 전달합니다. `--background` 중복 실행은 창을 띄우지 않습니다. 우클릭 메뉴의 `--preview`와 검증용 `--verify-startup`은 별도 프로세스에서 기존처럼 창을 닫으면 종료됩니다. 이전 버전 앱이 Space를 사용 중이거나 훅 등록에 실패하면 트레이 알림과 설정의 상태 문구에 사유가 표시됩니다.
- 같은 Space 단축키를 사용하는 다른 미리보기 프로그램이 있다면 한 프로그램에서만 활성화합니다.

## 검증 현황

자동 테스트는 `dotnet test tests/MoaView.Tests/MoaView.Tests.csproj --filter FullyQualifiedName~ExplorerPreviewTests`로 실행합니다. 전체 기존 회귀 테스트도 통과했습니다.

자동으로 확인한 항목:

- Space 길게 누르기와 키를 누른 채 포커스가 바뀌는 경우의 처리
- 열기, 같은 선택 중복 로드 방지, 선택 변경, 선택 해제, 닫기, 재열기
- 늦은 Shell 응답, 열기 취소, 조회 중 탭 변경, 종료 후 응답 폐기
- 실제 표시한 WPF 창의 이미지·미지원·오류 렌더링, 소유 창 연결, Space/Esc 닫기, 기본 창 유지
- 유효하지 않은 탐색기 핸들의 COM 조회와 선택 서비스 종료
- 실제 네이티브 키 훅 등록·해제·재등록, 세션 잠금 중복 획득 차단
- 상주 인스턴스 중복 차단, 백그라운드/파일 요청 전달, 비정상 클라이언트 시간 초과 후 복구, 종료 후 재시작
- 격리된 임시 레지스트리에서 자동 시작 등록·해제, 공백 포함 실행 경로, 다른 프로그램 값 보존

2026-11-09 개발 빌드에서는 현재 PC의 실제 탐색기에서 `--background`로 실행한 뒤 `icon.png`를 Space로 열고 닫았습니다. 기본 창을 열었다 닫은 뒤에도 같은 동작이 유지됐고, 재실행한 프로세스는 기존 프로세스의 창을 열고 코드 0으로 종료했습니다. 별도 WPF 실행 검증으로 트레이 메뉴의 열기·Space 전환·종료와 아이콘/훅 해제를 확인했습니다. Windows 로그인 자체와 설치·제거는 이번 검증에서 실행하지 않았습니다.

Windows 11 26H2에서 0.1.0이 탐색기 Shell 뷰의 COM 인터페이스 조회에 실패해 선택을 읽지 못하는 문제를 재현했습니다. 0.1.1에서는 `IShellView`를 통해 활성 뷰 핸들을 얻도록 수정했고, 같은 탐색기 창에서 선택 파일 경로를 정상 반환하는 것을 확인했습니다. 키 입력부터 미리보기 열기·닫기까지의 검증은 아래 항목으로 이어집니다.

| 확인 항목 | 기대 결과 | 현재 상태 |
| --- | --- | --- |
| Windows 10/11에서 이미지 하나 선택 후 Space 두 번 | 탐색기 포커스를 유지하며 열기·닫기 | 2026-11-12 Windows 11 26H2 확인, Windows 10 미확인 |
| Space를 길게 누르기 | 한 번만 열기 또는 닫기 | 격리 WPF 창 + 네이티브 훅 재등록·키 반복/키업 복구 자동 검증 완료 (`ExplorerPreviewTests`), 실제 탐색기 수동 확인 잔여 |
| 화살표·마우스로 다른 이미지/손상 파일 선택 | 선택 결과에 맞는 이미지·오류 표시 | 2026-11-12 PNG·GIF·바이너리·손상 PNG·ZIP 전환 확인 |
| 주소창·검색창·파일명 편집에서 Space | 공백이 정상 입력되고 미리보기는 열리지 않음 | 2026-11-12 현재 PC 확인, 파일명 편집은 취소하여 원본 유지 |
| Windows 11 탭 전환 | 활성 탭의 항목만 표시 | 동일 HWND 내 탭(`ViewHandle`) 전환·즉시 Space·동일 경로·빈 탭 WPF 렌더링 자동 검증 완료 (`ExplorerPreviewTests`), 실제 탐색기 수동 확인 잔여 |
| 탐색기 창 종료·재시작 | 이전 창 정리, 새 탐색기에서 다시 동작 | 소유 HWND 종료(`IsWindow == false`) 시 이전 창 자동 정리 및 새 HWND 재열기 자동 검증 완료 (`ExplorerPreviewTests`), 실제 탐색기 수동 확인 잔여 |
| 모아뷰 재실행 | 기존 상주 프로세스로 창 열기·파일 전달, 트레이 중복 없음 | 창 열기는 현재 PC 확인, 파일 전달은 자동 테스트 확인 |
| 기본 창 닫기 후 Space | 트레이 상태에서 이미지 열기·닫기 유지 | 현재 PC 확인 |

2026-11-12 QUIC-7은 다른 탐색기 창으로 이동한 직후 Space를 누를 때 이전 미리보기만 닫히는 경계를 수정했습니다. 실제 화면 검증은 당시 설치된 0.1.12에서 수행했고, 새 전환·지연 응답·취소 수정은 별도 작업 폴더의 회귀 테스트로 검증했습니다. 이어서 QUIC-10에서 소유 탐색기 창 종료(`IsWindow == false`) 시 포커스가 탐색기 밖으로 이동한 상태에서도 이전 미리보기 창과 상태를 정리하도록 보강하고, 탭 전환·창 종료 후 재시작·Space 길게 누르기의 실제 WPF 창 결합 자동 검증과 환경 제약을 정리했습니다. 상세 범위와 한계는 [QUIC-7 검증 기록](QUIC-7-usability-verification.md) 및 [QUIC-10 잔여 시나리오 검증 기록](QUIC-10-residual-scenario-verification.md)을 따릅니다.

## 구현 참고

키 훅은 별도 메시지 루프 스레드에서 Space와 수정키 상태만 검사하고 UI 스레드로 요청을 전달합니다. Shell COM 조회는 별도 STA 스레드에서 수행하며, 닫기·종료·포커스 변경 이후 반환된 오래된 결과를 적용하지 않습니다. 입력 내용이나 클립보드를 저장하지 않습니다.

탭마다 같은 최상위 HWND를 사용할 수 있으므로 현재 포커스의 Shell 뷰 HWND와 COM이 반환한 뷰 HWND를 함께 비교합니다. 네이티브 클래스 이름에 의존하는 포커스 판별은 Windows 탐색기 버전이 바뀌면 추가 실환경 확인이 필요합니다.

- [LowLevelKeyboardProc와 훅 스레드](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)
- [GetGUIThreadInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getguithreadinfo)
- [ShellFolderView.SelectedItems](https://learn.microsoft.com/en-us/windows/win32/shell/shellfolderview-selecteditems)
- [IShellBrowser.QueryActiveShellView](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishellbrowser-queryactiveshellview)
